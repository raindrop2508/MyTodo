# 数据流转方案评估

> 文档版本：v1.0  
> 更新日期：2026-06-28  
> 评估对象：MyPotato（番茄钟 TODO 应用，Android 原生）  
> 评估背景：Stage A（UI 骨架）已完成，各页面 Mock 数据独立，无数据互通；需在 Stage B 启动前确定数据流转方案

---

## 一、评估背景与目标

### 1.1 现状

当前项目数据层存在以下问题：

- **5 处 Mock 数据各自独立**：Today（5 条）、Tasks（4 条）、TaskDetail（5 步骤）、TaskEdit（占位步骤）、Statistics（硬编码），无统一数据源。
- **数据模型重复定义**：`TodayTask`、`TaskUiModel`、`StepMock`、`EditableStep` 字段高度相似但分散。
- **页面间无状态同步**：Today 页勾选完成，Tasks 页无感知；TaskEdit 保存后列表不刷新。
- **Room 仅有一张 `AppInfo` 表**，业务实体未落地。

### 1.2 评估目标

针对"独立开发者 + AI 工具辅助"的工作流特点，从以下四个维度评估三个候选方案：

1. **技术可行性**：方案能否落地，技术复杂度如何。
2. **开发效率**：对项目周期的影响，能否快速跑通流程。
3. **维护成本**：后续清理/切换的工作量，技术债大小。
4. **数据库整合兼容性**：与后续 Room 落地的衔接平滑度。

### 1.3 评估原则

- 不为迎合而妥协：若方案不适合当前场景，直接指出。
- 透明评估：缺点、技术债、长期维护成本与优点同等清晰展现。
- 批判性思维：警惕过度设计与盲目追求"快"而忽视"稳"。

## 二、方案1：JSON 临时存储方案

### 2.1 方案描述

构建 JSON 文件作为临时数据载体（可存于 SharedPreferences、内部存储或 assets），页面间通过读写 JSON 实现数据流转，为后续 Room 字段及表结构定义奠定基础。

### 2.2 优势

| 优势 | 说明 |
|------|------|
| 比 Room 直接落地略轻 | 无需定义 Entity/DAO，初期编码量略少 |
| JSON 结构可作表结构参考 | 字段定义可为后续 Room Entity 提供借鉴 |
| 解耦 UI 与持久层 | UI 通过 JSON 读写，不直接依赖 Room |

### 2.3 劣势与风险（直言）

| 劣势 | 说明 |
|------|------|
| 本质是重造一个简陋数据库 | 需自行实现序列化/反序列化、ID 生成、CRUD、并发控制、错误恢复，这些 Room 已内置 |
| 性能差 | JSON 全量读写，数据量增大后 IO 与解析卡顿明显；无索引、无 SQL 查询能力 |
| 无查询能力 | 筛选/排序/聚合需在内存中手写，Tasks 页的多维筛选会变得繁琐 |
| 并发不安全 | 多页面并发写同一 JSON 文件极易数据丢失/不一致，需自建锁机制 |
| 废弃成本高 | 后续切换 Room 时，所有 JSON 访问点都要替换，调用面与直接用 Room 等同，但中间多了一层废弃代码 |
| 与 Local First 目标弱相关 | JSON 适合配置/导入导出格式，不适合作为运行时主数据存储 |

### 2.4 适用场景

仅适合**极早期纯演示原型**，且明确很快会被替换。若原型生命周期超过数天或需演示真实交互，性价比急剧下降。

### 2.5 对项目周期影响与清理成本

- **周期影响**：看似省了 Room 定义时间，实则要在 JSON 序列化、ID 管理、并发控制上付出等同工作量。对独立开发者而言，净节省接近于零，甚至为负。
- **清理成本**：高。JSON 访问点分散各页面，切换 Room 时需逐个替换；若中途 JSON 结构频繁变动，迁移成本进一步上升。

### 2.6 业界视角

JSON 作为配置文件、导入导出格式是业界标准做法；但作为 Android 应用的**运行时主数据存储**是反模式。Android 官方明确推荐 Room/DataStore 用于结构化数据持久化。该方案属于"为了不建库而建了一个伪数据库"。

## 三、方案2：直接构建数据库方案

### 3.1 方案描述

直接设计 Room 数据库，定义 Task/TaskStep/Category/PomodoroSession 等实体与 DAO，配套 Repository 层，逐步将各页面数据迁移为从数据库读取。

### 3.2 优势

| 优势 | 说明 |
|------|------|
| 一步到位，无废弃中间层 | 符合大纲 Stage C 既定方向，无废弃代码 |
| 响应式数据同步 | Room + LiveData/Flow 天然实现页面间数据同步，Today 勾选 Tasks 即时刷新 |
| 查询/筛选/排序交给 SQL | Tasks 页多维筛选、Statistics 聚合均可由 SQL 高效完成 |
| 数据持久化 | 重启不丢数据，符合 Local First 目标 |
| 业界标准做法 | Room 是 Android 官方推荐的本地持久化方案，Repository + Room 是成熟范式 |
| 为统计页打基础 | 统计页延后的决策依赖数据库字段与内容，直接建库正好满足"待数据库落地后确定展示信息"的前提 |

### 3.3 劣势与风险（直言）

| 劣势 | 说明 |
|------|------|
| 前期设计成本高 | 表结构、关系、索引、外键级联、迁移策略需仔细规划 |
| 表结构设计不当有返工风险 | 字段缺失或类型不当需数据库迁移 |
| 短期压力大 | 单开发者需同时处理 UI 适配 + 数据层搭建 |
| 需 Repository 层配套 | 否则 UI 直接依赖 DAO，后续测试与替换困难 |

### 3.4 返工风险评估

- **返工概率：中低**。大纲已给出详细数据模型（Task/TaskStep/Category/PomodoroSession 字段完整），直接参考可大幅降低设计风险。
- **返工影响：可控**。开发期采用 `fallbackToDestructiveMigration`，字段扩展仅需加列 + 迁移脚本，无需推倒重来。
- **关键约束**：先定义最小字段集（满足当前 UI 需求），后续按需扩展，避免一次性过度设计。

### 3.5 对项目稳定性影响

- **稳定性：好**。Room 经工程验证，事务保证数据一致性，优于自建 JSON 方案。
- **风险点**：UI 与 Room 同时改造期间，短期内可能出现 UI 与数据不匹配的过渡态。对策是分批迁移，每完成一个页面即验证。

### 3.6 业界视角

这是标准且推荐的做法。Google 官方架构指南推荐 Room + Repository + ViewModel + LiveData/Flow 的分层模式。Local First 应用几乎都采用此路径。

### 3.7 实施难度

- **难度：中等**。Room 本身学习曲线平缓，AI 工具对 Room 样板代码生成非常成熟。
- **关键难点不在 Room，而在 Repository 接口设计**：接口契约定义得当，Fake/Room 可平滑切换。

## 四、方案3：基于现有 mock 数据通过类属性方式实现数据流转

### 4.1 方案描述

将各页面分散的 Mock 数据集中到一个单例对象（如 Kotlin `object` 单例或共享 ViewModel），通过类属性/方法实现页面间数据共享与流转。

### 4.2 优势

| 优势 | 说明 |
|------|------|
| 改动最小 | 仅需将分散 Mock 数据搬入单例，最快能跑通页面间数据互通 |
| 无新依赖 | 不引入 Room/JSON 库 |
| 内存操作 | 性能好，无 IO |

### 4.3 劣势与风险（直言）

| 劣势 | 说明 |
|------|------|
| 反模式 | 单例 + 可变状态是典型反模式，难测试、易出并发问题、生命周期管理混乱 |
| 不持久化 | 重启数据丢失，与 Local First 目标直接冲突 |
| 与数据库整合衔接差 | 切换 Room 时，所有单例访问点都要替换为 Repository 调用，迁移成本等同方案2，但没积累表结构知识 |
| 不为表结构定义提供帮助 | 类属性 ≠ 表结构，无法为 Room Entity 设计提供有效参考 |
| 生命周期错位 | 单例不跟随 Activity/Fragment 生命周期，易引发内存泄漏与状态错乱 |
| 仅是"把分散的坏集中成另一种坏" | 治标不治本，数据互通问题被推迟而非解决 |

### 4.4 技术合理性

- **短期可行**：能快速演示数据互通。
- **长期不合理**：作为正式数据流转方案，违背单一职责与状态可观测原则。单例可变状态在 Android 中尤其危险（配置变更、进程重建后状态丢失）。

### 4.5 扩展性

- **差**。单例随业务增长会膨胀为"上帝对象"（God Object），所有页面耦合到一个全局状态，难以拆分。

### 4.6 与数据库整合衔接

- **衔接差**。单例访问与 Repository 调用是两种完全不同的范式，切换时调用点全改，且单例中积累的业务逻辑（筛选/排序）需迁移到 SQL 或 Repository。

### 4.7 业界视角

单例共享状态在小型 Demo 可接受，但作为正式数据流转方案是反模式。Android 官方明确推荐通过 ViewModel + Repository + 持久层管理状态，而非全局可变单例。

## 五、方案对比矩阵

|---------|----------------------|------------------|-------------------|
| 技术可行性 | 可行但反模式 | ✅ 标准做法 | 可行但反模式 |
| 开发效率 | 净节省接近零 | 中等（AI 辅助下高） | ✅ 最快 |
| 维护成本 | 高（废弃中间层） | ✅ 低（无废弃） | 高（迁移等同重做） |
| 数据库整合兼容性 | 中（结构可借鉴） | ✅ 高（一步到位） | 差（不积累表结构知识） |
| 数据持久化 | 弱 | ✅ 强 | ✗ 无 |
| 页面间数据同步 | 需手写 | ✅ LiveData/Flow 天然 | 内存共享 |
| 查询/筛选/排序能力 | 手写 | ✅ SQL | 手写 |
| 并发安全 | 差 | ✅ 事务保证 | 差 |
| 业界认可度 | 反模式 | ✅ 官方推荐 | 反模式 |
| 技术债 | 高 | ✅ 低 | 高 |
| 适用阶段 | 极早期原型 | ✅ 正式开发 | 极早期原型 |

## 六、推荐方案与理由

### 6.1 推荐结论

**推荐方案2（直接构建数据库），但采用"Repository 接口先行 + Fake 先行 + Room 渐进替换"的渐进落地路径。**

### 6.2 选择理由

1. **符合大纲既定路径**：大纲 Stage B（Fake Repository）→ Stage C（Room 落地）本就是渐进式建库路径，方案2 与大纲完全一致，有文档支撑。

2. **避免方案1的废弃中间层**：JSON 临时存储付出的工作量不比直接建 Room 小多少（需自实现 CRUD/序列化/ID/并发），却得到一个注定废弃的中间层。对独立开发者，这是"做了两遍"的浪费。AI 工具对 Room 样板代码生成已非常成熟，Room 的学习成本不再是阻碍。

3. **规避方案2的一次性落地压力**：通过 Repository 接口 + FakeRepository 先行，让 Today/Tasks 快速接入统一数据源跑通主流程，再切换 RoomRepository。UI 通过 Repository 接口取数，切换时 UI 无感知。这既吸收了方案3"快速跑通"的优点，又避免了方案3的反模式与废弃成本。

4. **为统计页延后决策提供前提**：用户明确"统计页待数据库落地及番茄钟等核心功能完全实现后，根据实际数据库中的数据结构和内容确定展示信息"。方案2 直接落地数据库，正好满足这一前提；方案1/3 都无法提供真实数据库内容供统计页决策。

5. **响应式数据同步是刚需**：页面间数据互通是当前最大痛点。Room + LiveData/Flow 天然解决，无需自建同步机制。

6. **Local First 目标对齐**：应用定位为离线优先，数据持久化是基本要求。方案2 一步到位，方案1/3 都只是把持久化问题推迟。

### 6.3 不推荐方案1 的理由

JSON 适合作为导入导出格式（Stage E 的数据导入导出功能可用 JSON/CSV），但不适合作为运行时主数据存储。它的所有"优势"（轻量、解耦）在 Room 面前都不成立，而它的劣势（无查询、并发不安全、废弃成本高）是硬伤。

### 6.4 不推荐方案3 的理由

类属性流转的唯一价值"快速跑通"，在"Repository + FakeRepository"路径下同样可以实现，且无反模式代价。单例可变状态的并发、生命周期、扩展性问题是埋下未来技术债，不符合"最小功能原则"与"可维护性"要求。

## 七、推荐方案的实施步骤建议

采用"接口先行、Fake 先行、Room 渐进替换"三步走策略：

### 7.1 第一步：定义领域模型与 Repository 接口（接口先行）

1. 定义 domain model：`Task`、`TaskStep`、`Category`（参考大纲 7.1-7.3 字段，先取最小集）。
2. 定义 `TaskRepository` 接口，方法覆盖当前 UI 需求：
   - `getTasks(): LiveData<List<Task>>`
   - `getTaskById(id: Long): Task?`
   - `getStepsByTaskId(taskId: Long): LiveData<List<TaskStep>>`
   - `addTask(task: Task): Long`
   - `updateTask(task: Task)`
   - `toggleTaskDone(id: Long)`
   - `deleteTask(id: Long)`
3. 接口返回类型优先用 `LiveData` 或 `Flow`，为响应式刷新铺路。

**产出**：接口契约文档 + domain model + Repository 接口。AI 可据此生成样板代码，人工 review 接口设计。

### 7.2 第二步：实现 FakeRepository，迁移 Mock 数据（Fake 先行）

1. 实现 `FakeRepository`：内存 `MutableList` 持有数据，实现 `TaskRepository` 接口。
2. 将 5 处分散 Mock 数据统一迁入 `FakeRepository`，删除各页面 `buildMockTasks()`。
3. 各页面接入 Repository：通过 ViewModel 暴露 Repository 数据，UI 订阅 LiveData。
4. 打通三条主流程：新建 → 保存 → 列表刷新；编辑 → 保存 → 详情刷新；完成 → 状态同步。
5. 规则一致性校验：单次任务在所有入口无法进入番茄钟。

**产出**：页面间数据互通、三条主流程闭环、单一数据源。此阶段已解决用户描述的"页面数据独立、无互通"问题。

### 7.3 第三步：落地 Room，渐进替换 FakeRepository（Room 渐进替换）

1. 定义 Room Entity（`TaskEntity`/`TaskStepEntity`/`CategoryEntity`）+ DAO + Database。
2. 实现 `RoomRepository`，实现同一 `TaskRepository` 接口。
3. 在 `AppDatabase` 中扩展业务实体表，提供迁移脚本。
4. 依赖注入切换：将 `FakeRepository` 替换为 `RoomRepository`（UI 无感知，因接口不变）。
5. 引入 LiveData/Flow 响应式刷新，移除手动刷新逻辑。
6. 分批迁移验证：先 Today/Tasks，再 TaskDetail/Edit，最后 Pomodoro。
7. 统计页延后，待番茄钟会话落库后再开发。

**产出**：数据持久化、重启不丢失、响应式同步、为统计页提供真实数据基础。

### 7.4 实施节奏建议

- **不要一次性全量迁移**：每完成一个页面的 Repository 接入即验证，避免大爆炸式改动。
- **接口契约稳定**：Repository 接口一旦定义，Fake 与 Room 实现必须遵守，避免实现侧偷偷加方法。
- **测试先行**：对 Repository 层写契约测试（Fake 与 Room 跑同一套测试），确保行为一致。

## 八、风险与对策

| 风险 | 对策 |
|------|------|
| Repository 接口设计不当导致 Fake/Room 行为不一致 | 接口返回类型统一用 LiveData/Flow；写契约测试覆盖关键场景 |
| Room 表结构后续需扩展 | 字段集先最小后扩展；开发期用 `fallbackToDestructiveMigration`；正式版前补齐迁移脚本 |
| FakeRepository 与 RoomRepository 切换期数据不一致 | 切换前清空 Fake 数据；切换后从空库开始验证；提供数据初始化种子（默认 Category） |
| 单开发者短期压力大 | 严格分批迁移，每页验证；AI 辅助生成样板代码；不跨阶段并行大改 |
| 统计页延后导致 Room 字段过度设计 | 统计页所需字段（如 PomodoroSession）在 Stage D 再落地，Stage C 仅落 Task/TaskStep/Category |

## 九、结论

| 项 | 结论 |
|----|------|
| 推荐方案 | 方案2（直接构建数据库），采用"Repository 接口先行 + Fake 先行 + Room 渐进替换"渐进路径 |
| 核心理由 | 符合大纲既定路径、无废弃中间层、满足 Local First 与响应式同步、为统计页延后决策提供前提 |
| 阶段衔接 | 第二步 FakeRepository 即对应大纲 Stage B，第三步 Room 落地对应大纲 Stage C |
| 关键约束 | Repository 接口契约稳定、分批迁移每页验证、字段集先最小后扩展 |

> 本评估结论将作为 Stage B 启动的数据流转方案决策依据。后续实施以 [项目整体规划文档.md](file:///c:/code/MyTodo/docs/plan/项目整体规划文档.md) 的里程碑为准。
